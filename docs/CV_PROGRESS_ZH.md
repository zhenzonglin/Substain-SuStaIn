# 无sudo、首个CV缓存尚未写出时的独立计时

本文保留旧版运行的诊断方法。新版已提供正式分块和内部心跳，旧任务迁移请使用[安全切换说明](ACCELERATION_ZH.md)；不能通过仅编辑源码给已运行的旧worker添加心跳。

高CPU和累计CPU时间增加只能证明进程在执行，不能证明EM收敛、内部轮数增加或预计何时结束。当前旧worker没有EM心跳，普通用户的py-spy已被工作站权限拦截；更换gdb/strace通常不能解决同一限制。不要把独立探针的输出当成旧worker的内部进度。

## 原实现的边界

固定官方版本每个起点EM最多100轮，每轮依次搜索事件的候选位置。当前38特征产生114事件，一个K模型还需25起点、三轮各10000次MCMC调优、100000次正式采样及留出评估后才写出pickle。源码未发现第一个K模型未完成时由本包装器自动反复重启的逻辑；这仍不能代替对活进程的直接观察。

## 在另一终端运行独立探针

```bash
cd /data02/linzhenzong/Substain-SuStaIn &&
git pull --ff-only &&
.venv/bin/python scripts/probe_cv.py --config config/local.38.yaml
```

所有参数在config/cv_probe.yaml：默认复现fold 0、K=1、startpoint 0的原种子与全部训练样本，保留正式特征和阈值。额外一个低优先级进程，BLAS单线程，每5秒输出一次心跳，最多一轮EM或600秒。内存预计超过8GiB或预计剩余可用内存不足16GiB时拒绝计算。诊断计时会增加少量CPU/内存带宽竞争；其耗时不能直接等同于旧worker的耗时。

探针核对CV配置、输入、参考、源码、依赖、分折和种子身份。它调用原官方函数，只在自己的独立实例上包一层计数和计时，不改官方安装文件、不改正式入口、不写正式分析目录、不停止旧任务。达到时间上限只终止自己创建的子进程。Ctrl+C也只结束这个诊断任务。

## 结果的解读

- 似然调用完成数持续增长：新的独立实例在完成真实数值计算；不是旧worker的推进证据。
- 一轮EM完成、有限的候选logL和顺序变化：同一输入上的一轮官方搜索可以完成。logL不变也可能是已达到局部最优，不能单凭这一点判定空转。
- 一轮EM耗时很长：支持当前问题可能是算法计算量大；不能据单轮耗时计算完整CV剩余时间，各起点、各轮和不同K成本不同。
- time_limit且没有完整EM轮：仅获得部分调用计时，不是失败或完整模型；不能判定旧任务卡死。
- 非有限值、身份不符或异常：保留错误，进一步定位；不要据此自动删除或重启正式结果。

诊断输出位于.cache/cv_probe/时间戳/：settings.yaml、input_identity.json、progress.json、result.json和launcher.json。若父进程硬超时，result.json可能没有写出，以launcher.json和最后的progress.json为准。这些文件只含配置、摘要和哈希；不导出患者行、MRI或正式后验。诊断文件不进入GitHub。

## 开发端验收与实际工作站边界

已验证独立观察器与原官方调用的完整起点序列、亚型比例及似然一致；真实38维114事件一轮EM完成；诊断前后正式文件字节与mtime不变；身份漂移、内存不足、输出越界均拒绝；时间预算不会伪称完成，超时只停止诊断子进程。所有验收使用合成数据，不能替代工作站真实C3计时，更不能排除旧worker空转。
